Puzzle 18: Softmax

The softmax function transforms a vector of arbitrary real numbers into a probability distribution. Given input vector x of length N, softmax produces output y where each element is:

\[ y_i = \frac{e^{x_i}}{\sum_{j=1}^{N} e^{x_j}} \]

It has two key steps:

  1. Compute the exponentials of the input vector
  2. Normalize the exponentials to sum to 1.0

Each output is positive, between the range [0,1], and they sum to 1.0.

The Numerical Stability Problem

Naive softmax fails on real data with extreme values[1] because of overflow. Consider computing softmax([1000, 1001, 1002]):

import numpy as np
x = np.array([1000., 1001., 1002.])
exp_x = np.exp(x)  # [inf, inf, inf] - overflow!
softmax = exp_x / exp_x.sum()  # [nan, nan, nan]

The exponentials overflow float32 before we even reach the division. Even float64 only buys you a bit more headroom — exp(710) still overflows.

Safe Softmax: The Max-Subtraction Trick

The safe softmax implementation exploits a mathematical identity: softmax is translation invariant[2]. Subtracting any constant from all inputs doesn’t change the output:

\[ \frac{e^{x_i - c}}{\sum_{j} e^{x_j - c}} = \frac{e^{x_i} \cdot e^{-c}}{\sum_{j} e^{x_j} \cdot e^{-c}} = \frac{e^{x_i}}{\sum_{j} e^{x_j}} \]

By choosing \(c = \max(x)\), we ensure the largest exponent is zero, preventing overflow while maintaining numerical precision:

\[ \text{softmax}(x_i) = \frac{e^{x_i - \max(x)}}{\sum_{j=1}^{N} e^{x_j - \max(x)}} \]

Now our example works:

x = np.array([1000., 1001., 1002.])
x_shifted = x - x.max()  # [-2, -1, 0]
exp_x = np.exp(x_shifted)  # [0.135, 0.368, 1.0]
softmax = exp_x / exp_x.sum()  # [0.09, 0.244, 0.665] ✓

Parallel Softmax: Two-Pass Reduction

Computing softmax on GPU requires two parallel reductions (recall Puzzle 10’s dot product reduction):

Pass 1: Find maximum - Each thread loads one element into shared memory - Parallel tree reduction to find max(x) - Result stored in shared[0]

Pass 2: Compute exponentials and sum - Each thread computes exp(x[i] - max_val) - Store in shared memory - Parallel reduction to find sum of exponentials - Each thread divides by the sum to get final softmax value

alias SIZE = 128
alias TPB = 128  # Next power of 2 >= SIZE
alias BLOCKS_PER_GRID = (1, 1)
alias THREADS_PER_BLOCK = (TPB, 1)
alias dtype = DType.float32
alias layout = Layout.row_major(SIZE)

fn softmax[
    layout: Layout
](
    output: LayoutTensor[mut=True, dtype, layout],
    a: LayoutTensor[mut=False, dtype, layout],
    size: Int,
):
    global_i = block_dim.x * block_idx.x + thread_idx.x
    local_i = thread_idx.x

    # Allocate shared memory for reduction
    shared = tb[dtype]().row_major[TPB]().shared().alloc()

    # Load input into shared memory
    if global_i < size:
        shared[local_i] = a[global_i]
    else:
        shared[local_i] = -SIMD[dtype, 1].MAX  # Neutral value for max

    barrier()

    # ============ Pass 1: Find Maximum ============
    var stride = TPB // 2
    while stride > 0:
        if local_i < stride:
            shared[local_i] = max(shared[local_i], shared[local_i + stride])
        barrier()
        stride //= 2

    # All threads now see max in shared[0]
    var max_val = shared[0]
    barrier()

    # ============ Pass 2: Exponentials and Sum ============
    # Compute exp(x - max) for numerical stability
    if global_i < size:
        shared[local_i] = exp(a[global_i] - max_val)
    else:
        shared[local_i] = 0.0  # Neutral value for sum

    barrier()

    # Parallel reduction to find sum of exponentials
    stride = TPB // 2
    while stride > 0:
        if local_i < stride:
            shared[local_i] += shared[local_i + stride]
        barrier()
        stride //= 2

    # Normalize by sum to get softmax
    var sum_exp = shared[0]
    if global_i < size:
        output[global_i] = exp(a[global_i] - max_val) / sum_exp

Why Two Barriers Between Passes?

Notice the pattern:

barrier()  // End of max reduction
var max_val = shared[0]
barrier()  // Before starting exp computation

The second barrier is crucial. After the max reduction completes, thread 0 has written the result to shared[0], but other threads immediately start overwriting their shared memory slots with exponential values. Without the middle barrier, a thread could read a stale max value while thread 0 is still writing it.

Rule of thumb: Every phase that writes to shared memory needs a barrier before the next read.

Performance Notes

For this SIZE=128 example, softmax is memory-bound. The arithmetic intensity is:

\[ I = \frac{3N \text{ FLOPs}}{8N \text{ bytes}} = 0.375 \text{ FLOP/byte} \]

(3N operations: N subtracts, N exponentials, N divides; 8N bytes: read input twice, write output)

This is far below our RTX 4090’s critical intensity of ~74 FLOP/byte, so performance is limited by DRAM bandwidth, not compute. The shared memory reductions add minimal overhead—most time is spent in the initial load and final store.

Puzzle 19: Attention

Attention is the core operation in transformers. Given a query vector Q, a set of key vectors K, and corresponding value vectors V, attention computes a weighted sum of values where the weights are determined by the similarity between the query and each key.

The Attention Formula

\[ \text{Attention}(Q, K, V) = \text{softmax}(Q \cdot K^T) \cdot V \]

Where: - Q (query): shape (d,) — what we’re looking for - K (keys): shape (seq_len, d) — what each position offers - V (values): shape (seq_len, d) — the actual content at each position - Output: shape (d,) — weighted combination of values

Think of it like a searchlight. The query is your search beam, keys are the labels on doors, and values are what’s behind each door. The dot product Q·K^T measures how well each key matches your query. Softmax converts these scores into weights that sum to 1.0. Finally, you take a weighted average of the values.

Three-Step Computation

Step 1: Compute Attention Scores

\[ \text{scores} = Q \cdot K^T \quad \text{shape: } (1, \text{seq\_len}) \]

This is a matrix-vector multiplication. For each key vector, we compute the dot product with the query:

scores[i] = Q[0]·K[i,0] + Q[1]·K[i,1] + ... + Q[d-1]·K[i,d-1]

Higher scores mean the key is more relevant to the query.

Step 2: Compute Attention Weights

\[ \text{weights} = \text{softmax}(\text{scores}) \quad \text{shape: } (1, \text{seq\_len}) \]

We apply our softmax kernel from Puzzle 18 to normalize scores into probabilities. This ensures all weights are positive and sum to 1.0.

Step 3: Weighted Sum of Values

\[ \text{output} = \text{weights} \cdot V \quad \text{shape: } (d,) \]

Another matrix-vector multiplication. Each output dimension is computed as:

output[j] = weights[0]·V[0,j] + weights[1]·V[1,j] + ... + weights[seq_len-1]·V[seq_len-1,j]

Memory Efficiency: The Key Trick

Notice that scores and weights have the same shape (1, seq_len). We can reuse the same buffer for both:

  1. Allocate scores_weights_buf of size (1, seq_len)
  2. Compute scores into this buffer
  3. Apply softmax in-place, overwriting scores with weights
  4. Use the buffer (now containing weights) for the final matmul

This halves memory usage compared to allocating separate buffers.

Kernel Orchestration

Instead of writing a monolithic attention kernel, we compose three optimized kernels we already have:

  1. Transpose kernel (new!) — compute K^T efficiently
  2. Matmul kernel (Puzzle 14) — compute Q·K^T
  3. Softmax kernel (Puzzle 18) — normalize scores
  4. Matmul kernel (again) — compute weights·V

This modular approach has several benefits: - Each kernel is simpler to optimize independently - We reuse battle-tested implementations - Easier to maintain and debug - Natural parallelism between independent operations

Implementation: Transpose Kernel

The missing piece is an efficient transpose. Naive per-thread transpose is slow because of strided memory access. Instead, we use shared memory tiling to coalesce reads and writes:

Transpose with Shared Memory Tiling 
p19_transpose.mojo
alias TILE_SIZE = 16

fn transpose_2d[
    in_layout: Layout, out_layout: Layout
](
    output: LayoutTensor[mut=True, dtype, out_layout],
    input: LayoutTensor[mut=False, dtype, in_layout],
    rows: Int,
    cols: Int,
):
    # Global position
    row = block_idx.y * TILE_SIZE + thread_idx.y
    col = block_idx.x * TILE_SIZE + thread_idx.x

    # Allocate shared tile (+1 to avoid bank conflicts)
    shared = tb[dtype]().row_major[TILE_SIZE, TILE_SIZE + 1]().shared().alloc()

    # Cooperatively load tile into shared memory (coalesced)
    if row < rows and col < cols:
        shared[thread_idx.y, thread_idx.x] = input[row, col]

    barrier()

    # Transpose coordinates for output
    out_row = block_idx.x * TILE_SIZE + thread_idx.y
    out_col = block_idx.y * TILE_SIZE + thread_idx.x

    # Write transposed tile to global memory (coalesced)
    if out_row < cols and out_col < rows:
        output[out_row, out_col] = shared[thread_idx.x, thread_idx.y]

Key optimizations:

  1. Tile-based approach: Process 16×16 tiles to maximize shared memory reuse
  2. Coalesced reads: Adjacent threads read adjacent memory locations (good for input)
  3. Coalesced writes: Adjacent threads write adjacent locations in transposed space (good for output)
  4. Bank conflict avoidance: The +1 padding in the shared memory dimension prevents threads from hitting the same memory bank

Without tiling, a naive transpose would have either coalesced reads OR coalesced writes, but not both. The shared memory “pivots” the access pattern, giving us coalescing in both directions.

Zero-Copy Reshaping

Notice the pattern:

var scores_1d = scores.reshape[SEQ_LEN]()

This is a zero-copy operation. No data moves in memory—we simply reinterpret the tensor’s dimensionality. The underlying buffer remains unchanged. This is safe because:

  1. The total number of elements stays the same: 1 × SEQ_LEN = SEQ_LEN
  2. Memory layout (row-major) is compatible with both interpretations
  3. The LayoutTensor API enforces these invariants at compile time

This is one of Mojo’s killer features for systems programming—high-level abstractions that compile to zero-overhead code.

The Memory Problem

Our implementation works, but it’s inefficient. Let’s count the memory usage:

Temporary buffers: - K^T: D × SEQ_LEN × 4 bytes = 8 × 16 × 4 = 512 bytes - Scores/weights: SEQ_LEN × 4 bytes = 16 × 4 = 64 bytes - Total per attention call: ~600 bytes

This seems tiny, but consider a real transformer:

  • Sequence length: 2048
  • Hidden dimension: 4096
  • Number of heads: 32
  • Batch size: 16

Memory for attention scores alone:

16 (batch) × 32 (heads) × 2048 × 2048 × 4 bytes = 8.6 GB

With multiple layers and the backward pass, you quickly exceed even high-end GPU memory. The quadratic O(seq_len²) scaling is the bottleneck.

Flash Attention solves this by never materializing the full attention matrix. Instead, it computes attention in tiles, keeping everything in fast SRAM. But there’s a catch—we need a way to compute softmax without seeing all the scores at once.

Enter online softmax.

Online Softmax: The Missing Piece

The standard softmax implementation we built in Puzzle 18 requires two passes over the data:

  1. Find the maximum value
  2. Compute exponentials and their sum

This works when all values fit in memory, but Flash Attention processes attention scores in chunks. We need to compute softmax incrementally—updating our statistics as new values stream in, without storing everything.

The Mathematical Foundation

Recall the numerically stable softmax formula:

\[ \text{softmax}(x_i) = \frac{e^{x_i - m}}{\sum_{j} e^{x_j - m}} \quad \text{where } m = \max(x) \]

The key insight: we can maintain running statistics (max and sum) and rescale previous results when we see a new maximum.

Notation

For a partial sequence processed so far, we track: - \(m\) : current maximum seen - \(d\) : current sum of exponentials (denominator) - \(o\) : current weighted output (numerator)

When we process a new block with local max \(m'\) and sum \(d'\):

  1. Compare maximums: The new global maximum is \(m_{new} = \max(m, m')\)
  2. Rescale old statistics: Scale the old sum by \(e^{m - m_{new}}\) to account for the change in maximum
  3. Update sum: \(d_{new} = d \cdot e^{m - m_{new}} + d' \cdot e^{m' - m_{new}}\)
  4. Update output: \(o_{new} = o \cdot e^{m - m_{new}} + o' \cdot e^{m' - m_{new}}\)

The beauty: this update is exact, not an approximation. The final result is identical to computing softmax over the entire sequence at once.

Worked Example

Let’s compute softmax([1.0, 3.0, 2.0, 4.0]) in two blocks: [1.0, 3.0] and [2.0, 4.0].

Block 1: Process [1.0, 3.0]

m₁ = max(1.0, 3.0) = 3.0
e^(1.0 - 3.0) = e^(-2.0) = 0.135
e^(3.0 - 3.0) = e^(0.0) = 1.0
d₁ = 0.135 + 1.0 = 1.135

Current softmax: [0.135/1.135, 1.0/1.135] = [0.119, 0.881]

Block 2: Process [2.0, 4.0]

m₂' = max(2.0, 4.0) = 4.0
e^(2.0 - 4.0) = e^(-2.0) = 0.135
e^(4.0 - 4.0) = e^(0.0) = 1.0
d₂' = 0.135 + 1.0 = 1.135

Merge: Update Global Statistics

m_new = max(m₁, m₂') = max(3.0, 4.0) = 4.0

Rescale old statistics:
scale_old = e^(3.0 - 4.0) = e^(-1.0) = 0.368
scale_new = e^(4.0 - 4.0) = e^(0.0) = 1.0

d_new = d₁ × scale_old + d₂' × scale_new
      = 1.135 × 0.368 + 1.135 × 1.0
      = 0.418 + 1.135
      = 1.553

Final Softmax (all at once for verification)

Direct computation:
m = 4.0
exp_values = [e^(1-4), e^(3-4), e^(2-4), e^(4-4)]
           = [0.050, 0.368, 0.135, 1.0]
sum = 1.553

softmax = [0.050/1.553, 0.368/1.553, 0.135/1.553, 1.0/1.553]
        = [0.032, 0.237, 0.087, 0.644] ✓

The online approach gives identical results!

Why This Works: Softmax Decomposition

The mathematical property that enables online softmax is:

\[ \frac{e^{x_i - m_{global}}}{\sum_{j=1}^{N} e^{x_j - m_{global}}} = \frac{e^{x_i - m_{global}}}{e^{m_1 - m_{global}} \sum_{j \in B_1} e^{x_j - m_1} + e^{m_2 - m_{global}} \sum_{j \in B_2} e^{x_j - m_2}} \]

Where \(B_1, B_2\) partition the sequence and \(m_1, m_2\) are local maxima. The exponential terms \(e^{m_k - m_{global}}\) act as correction factors that rescale each block’s contribution.

This means: 1. We can compute local softmax for each block independently 2. Keep running totals of \(m\) and \(d\) 3. Rescale everything when we encounter a new maximum 4. The final normalization is exact

Implementation Sketch

fn online_softmax_update(
    inout m: Float32,        # current max
    inout d: Float32,        # current sum of exp
    inout o: Vector,         # current output
    scores: Vector,          # new block of scores
    values: Matrix,          # corresponding values
):
    # Find local maximum in new block
    var m_new = max(scores)

    # Compute local sum of exponentials
    var d_new: Float32 = 0.0
    for i in range(len(scores)):
        d_new += exp(scores[i] - m_new)

    # Compute new global maximum
    var m_global = max(m, m_new)

    # Rescaling factors
    var scale_old = exp(m - m_global)
    var scale_new = exp(m_new - m_global)

    # Update global sum
    d = d * scale_old + d_new * scale_new

    # Rescale old output and add new contribution
    o = o * scale_old + compute_weighted_sum(scores, values, m_new) * scale_new

    # Update maximum
    m = m_global

This is the core of Flash Attention. Instead of materializing the full seq_len × seq_len attention matrix, we process it in tiles, maintaining running statistics and updating them online.

The memory usage drops from O(seq_len²) to O(seq_len), storing only the current tile and running statistics.

Flash Attention 1: Tiled Attention with Online Softmax

Now we can understand the Flash Attention algorithm [3]. The key idea: never materialize the full attention matrix. Instead:

  1. Divide K and V into blocks
  2. Process one block at a time, computing partial attention outputs
  3. Use online softmax to merge results incrementally
  4. Keep everything in fast SRAM

The Algorithm

Here’s the Flash Attention forward pass in pseudocode:

def flash_attention_forward(Q, K, V, block_size):
    N, d = Q.shape
    O = zeros_like(Q)
    m = full(N, -inf)  # running max for each query
    d_sum = zeros(N)    # running sum of exp for each query

    # Divide Q into blocks of size block_size
    for q_start in range(0, N, block_size):
        q_end = q_start + block_size
        Q_block = Q[q_start:q_end]  # Load into SRAM

        # Initialize block statistics
        m_block = full(block_size, -inf)
        d_block = zeros(block_size)
        O_block = zeros((block_size, d))

        # Iterate over K, V blocks
        for kv_start in range(0, N, block_size):
            kv_end = kv_start + block_size
            K_block = K[kv_start:kv_end]  # Load into SRAM
            V_block = V[kv_start:kv_end]  # Load into SRAM

            # Compute attention scores for this tile
            S_tile = Q_block @ K_block.T  # (block_size, block_size)

            # Find local maximum
            m_new = max(S_tile, dim=1)

            # Compute local softmax numerators
            P_tile = exp(S_tile - m_new[:, None])
            d_new = sum(P_tile, dim=1)

            # Compute local weighted sum
            O_new = P_tile @ V_block

            # ===== Online Softmax Merge =====
            # New global max
            m_global = maximum(m_block, m_new)

            # Rescaling factors
            scale_old = exp(m_block - m_global)
            scale_new = exp(m_new - m_global)

            # Update running sum
            d_block = d_block * scale_old + d_new * scale_new

            # Update running output (rescale old, add new)
            O_block = O_block * scale_old[:, None] + O_new * scale_new[:, None]

            # Update max
            m_block = m_global

        # Final normalization
        O[q_start:q_end] = O_block / d_block[:, None]

    return O

Why Is It Faster?

Flash Attention is faster despite doing more work (recomputation, rescaling) because:

  1. Memory bandwidth dominates: Standard attention is memory-bound. Reading/writing the N² matrix from HBM is slow.

  2. SRAM is 10-20× faster: Flash Attention keeps working data in SRAM, only touching HBM for inputs/outputs.

  3. Arithmetic is cheap: Modern GPUs have massive compute. The extra rescaling operations are negligible compared to memory savings.

  4. Better cache utilization: Tiled access patterns are cache-friendly.

Recall the Roofline Model from Puzzle 14. By increasing arithmetic intensity (more FLOPs per byte moved), Flash Attention pushes attention from deep in the memory-bound region closer to the compute bound.

Backward Pass: Recomputation

One clever aspect of Flash Attention: the backward pass recomputes attention scores rather than storing them. This trades compute for memory—a good deal on modern GPUs where bandwidth is the bottleneck.

During backpropagation: 1. Recompute scores for each tile (same forward tiling pattern) 2. Compute gradients using stored output and running statistics 3. Still O(N) memory, but ~2× compute

The net result: training uses O(N) memory instead of O(N²) while being faster than naive attention.

Flash Attention 3: Exploiting Hopper’s Asynchrony [5]

Flash Attention 3, released in 2024, is purpose-built for NVIDIA’s Hopper architecture (H100 GPUs). The key insight: Hopper’s new hardware units enable asynchronous execution, allowing us to overlap computation with data movement.

The Hardware: TMA and WGMMA

Hopper introduces two game-changing features:

1. TMA (Tensor Memory Accelerator) - Dedicated DMA engine for HBM ↔︎ Shared Memory transfers - Handles address calculation and bounds checking automatically - Frees up registers that would otherwise track indices - Non-blocking: Issue multiple TMA loads without stalling

2. WGMMA (Warpgroup Matrix Multiply-Accumulate) - New Tensor Core instruction operating on warpgroups (4 warps = 128 threads) - 3× higher throughput than previous mma.sync instructions - Reaches 989 TFLOPS (vs. ~660 TFLOPS for older tensor cores) - But: Softmax only reaches 3.9 TFLOPS (special function units are slow!)

The performance imbalance between matmul (989 TFLOPS) and softmax (3.9 TFLOPS) is 253×. FA3’s goal: hide softmax latency behind matmul computation.

Innovation 1: Warp Specialization

Instead of all warps doing the same work, assign different roles to different warps:

Producer Warps (2-4 warps):
  - Issue TMA loads for Q, K, V tiles
  - Handle memory traffic
  - Don't do any computation

Consumer Warps (remaining warps):
  - Execute WGMMA for QK^T and PV
  - Perform softmax operations
  - Maximize tensor core utilization

The magic: While consumer warps compute on tile N, producer warps fetch tile N+1. Perfect overlap of compute and memory transfer.

Innovation 3: FP8 Incoherent Processing

Hopper supports FP8 (8-bit floats), cutting memory bandwidth by 50%. But not all operations tolerate low precision.

FA3’s precision strategy:

P·V matmul FP8 Another large matmul

How it works: 1. Store Q, K, V in FP8 in HBM (50% memory savings) 2. Load tiles into shared memory, convert to FP8 for WGMMA 3. WGMMA produces FP32 accumulator (hardware feature) 4. Softmax operates on FP32 scores 5. Write output back to HBM in FP16/FP32

Quality preservation techniques:

Block Quantization: Split Q, K, V tensors into blocks (e.g., 64×64 tiles) and quantize each block independently with its own scaling factor. This prevents outliers in one region from degrading precision everywhere.

Incoherent Processing: Multiply Q and K by a random Hadamard transform (orthogonal matrix with random signs). This “spreads out” outlier values that would otherwise cause large quantization errors.

Flash Attention 4: Pushing Blackwell to the Limit

Flash Attention 4, released alongside NVIDIA’s Blackwell architecture (SM100/Compute Capability 10.0), takes warp specialization to the extreme. Instead of 2 roles (producer/consumer), FA4 has 5 specialized roles, each optimized for specific hardware units.

The Hardware Challenge

Blackwell’s performance characteristics create new bottlenecks: - Tensor Cores: 2× faster than Hopper (2 PFLOPs for FP8) - Special Function Units (SFU): Only modest gains (~5 TFLOPs for exp/log) - TMA: Slightly improved bandwidth

The gap between matmul (2000 TFLOPs) and softmax (5 TFLOPs) is now 400×. FA3’s tricks aren’t enough—we need more aggressive parallelism.

Five Warp Roles

FA4 splits the attention kernel into a microservices architecture:

1. Load Warp (1 warp):
   - Issues all TMA loads for Q, K, V
   - Pure memory orchestration, zero compute

2. MMA Warp (1 warp):
   - Executes WGMMA for QK^T and PV
   - Maximizes tensor core utilization
   - Never waits on barriers

3. Softmax Warps (8 warps):
   - Parallel softmax reduction across multiple warps
   - Each warp handles a slice of the attention scores
   - Coordination via shared memory atomics

4. Correction Warps (4 warps):
   - Rescale output when max changes (online softmax)
   - Parallel correction across output dimensions
   - Previously a major bottleneck

5. Epilogue Warps (1-2 warps):
   - Write final output to global memory
   - Handle output buffering and staging

Total: 15-16 warps per thread block, each with a specialized role.

Key Innovation: Selective Rescaling

FA3 problem: Rescale output every time a new maximum is encountered. For long sequences, this happens frequently, wasting cycles on unnecessary corrections.

FA4 solution: Only rescale when the maximum changes significantly enough to affect numerical accuracy.

// FA3: Rescale on every new max
if m_new > m_old:
    correction_factor = exp(m_old - m_new)
    output *= correction_factor

// FA4: Rescale only when necessary
if m_new - m_old > RESCALE_THRESHOLD:  // Typically 1.0-2.0
    correction_factor = exp(m_old - m_new)
    output *= correction_factor

Why it works: If m_new - m_old < 1.0, then exp(m_old - m_new) ≈ 0.37-1.0, which is close enough that skipping the correction has <0.01% accuracy impact.

Result: 10× reduction in correction operations for typical workloads.

Innovation 2: Fast Polynomial Exponentials

The bottleneck: Special Function Units (SFUs) compute exp/log via hardware lookup tables. On Blackwell, SFUs have wave quantization effects—when many warps request exponentials simultaneously, they queue up.

FA4’s trick: For small head dimensions (≤128), use polynomial approximation instead of SFU:

\[ 2^x \approx c_0 + c_1 x + c_2 x^2 + c_3 x^3 \quad \text{for } x \in [0, 1] \]

Implemented via Horner’s method (3 fused multiply-adds):

fn fast_exp2(x: Float32) -> Float32:
    // Coefficients for cubic polynomial (minimax approximation)
    alias c3 = 0.0733664036
    alias c2 = 0.226894881
    alias c1 = 0.693058145
    alias c0 = 0.999999881

    // Horner's method: 3 FMAs instead of 1 SFU call
    return c0 + x * (c1 + x * (c2 + x * c3))

Trade-off: - Error: <0.0001 absolute error over [0, 1] - Cost: 3 FMA operations (3-6 cycles) vs. 1 SFU (20-50 cycles when queued) - Net win: 3-8× faster exponentials for attention-heavy workloads

Optimization 2: Shared Memory Swizzling (288 TFLOPs, 1.9× faster)

Shared memory has 32 banks serving requests in parallel. Without swizzling, multiple threads hit the same bank—causing sequential access (bank conflicts).

The Bank Conflict Problem

// Without swizzling: 8-way bank conflict
Thread 0: reads shared[0][0]   → Bank 0
Thread 1: reads shared[0][1]   → Bank 0  # conflict!
Thread 2: reads shared[0][2]   → Bank 0  # conflict!
...
Thread 7: reads shared[0][7]   → Bank 0  # conflict!

Result: Takes 8 cycles instead of 1 cycle.

Swizzle Pattern: <3,4,3> (128-byte swizzle)

The swizzle uses bitwise XOR to distribute data:

fn apply_swizzle[bits_y: Int, bits_x: Int, bits_z: Int](offset: Int) -> Int:
    # Extract bit fields
    let shift = bits_y + bits_x
    let mask = (1 << bits_y) - 1

    # XOR the middle bits with upper bits
    return offset ^ ((offset >> shift) & mask) << bits_x

For <3,4,3> swizzle: - 2³ = 8 rows per pattern - 2⁴ = 16 bytes per row - 2³ = 8 patterns cycling through 32 banks

Result: Adjacent threads access different banks. Zero bank conflicts.

The solution: Overlap operations with a 5-stage pipeline.

Cycle 1-5:   Load tile 0
Cycle 6-25:  Compute tile 0 | Load tile 1
Cycle 26-30: Write tile 0    | Compute tile 1 | Load tile 2
...

Warp Specialization for Pipelining

Assign different warps to different tasks:

enum WarpRole:
    LOAD_A      # Issues TMA for A tiles
    LOAD_B      # Issues TMA for B tiles
    MMA_EARLY   # Launches MMA on stage N
    MMA_LATE    # Launches MMA on stage N+1
    EPILOGUE    # Writes results to global memory

fn pipelined_kernel[pipeline_stages: Int = 5](...):
    var role = assign_warp_role(thread_idx.x // 32)

    @parameter
    if role == WarpRole.LOAD_A:
        for stage in range(num_iterations):
            # Wait for TMEM to be free
            mma_barrier[stage % pipeline_stages].wait(phase)

            # Load next A tile
            tma_a.async_copy(a_smem[stage % pipeline_stages], ...)

            # Signal data ready
            tma_barrier[stage % pipeline_stages].arrive()

    @parameter
    if role == WarpRole.MMA_EARLY:
        for stage in range(num_iterations):
            # Wait for data
            tma_barrier[stage % pipeline_stages].wait(phase)

            # Launch MMA
            tcgen05.mma(a_desc, b_desc, c_tmem, ...)

            # Signal TMEM consumed
            mma_barrier[stage % pipeline_stages].arrive()

Result: Load warps continuously feed data while MMA warps continuously compute. Near-100% utilization.

Optimization 6: Cluster Launch Control (1773 TFLOPs, SOTA!)

Final bottleneck: Kernel relaunch overhead. Traditional approach launches a kernel per batch of tiles, wasting cycles on: - Initializing shared memory - Scheduling CTAs to SMs - Synchronizing across launches

Cluster Launch Control (CLC): Hardware scheduler assigns work dynamically. A single persistent kernel runs continuously, with a scheduler warp distributing tiles.

fn persistent_kernel_with_clc(...):
    var scheduler_warp = (thread_idx.x // 32) == 0
    var num_tiles = (M / BM) * (N / BN) * (K / BK)

    if scheduler_warp:
        # Scheduler warp: Assign tiles to idle clusters
        var tile_idx = cluster_id()  # Start with own ID

        while tile_idx < num_tiles:
            # Write coordinates to shared memory
            shared_tile_coords[0] = tile_idx

            # Signal work ready
            work_barrier.arrive()

            # Try to claim next tile (atomic)
            tile_idx = atomic_add(global_tile_counter, num_clusters)
    else:
        # Worker warps: Process assigned tiles
        while True:
            # Wait for work assignment
            work_barrier.wait()

            var tile_idx = shared_tile_coords[0]
            if tile_idx >= num_tiles:
                break

            # Process this tile (normal matmul)
            ...

Benefit: Eliminates inter-kernel gaps. GPU stays saturated with work.

The Power of Tiling

Every optimization we’ve seen—from matmul to convolution to attention—relies on tiling:

  1. Divide problem into blocks that fit in fast memory
  2. Load each block once
  3. Maximize reuse within the block
  4. Minimize slow memory traffic

Flash Attention adds one more ingredient: online algorithms that let us process tiles sequentially without storing intermediate results.

Online Softmax: The Key Innovation

The mathematical trick that makes Flash Attention possible:

\[ \text{softmax}(\text{concat}(x, y)) = \text{merge}(\text{softmax}(x), \text{softmax}(y)) \]

By maintaining running statistics (max, sum, output) and rescaling when we see new maximums, we can compute exact softmax in a single pass over tiles. This is not an approximation—the result is bit-identical to standard softmax.

Each generation maintained backward compatibility (same API, same correctness) while adapting to new hardware capabilities. This is systems programming at its best.

Key Optimizations

1. Swizzled Shared Memory

alias K_SWIZZLE = Swizzle(2, 0, 2)  # Reduces bank conflicts

var k_buffer = SharedMemoryBuffer[
    dtype,
    Layout.row_major(BLOCK_N, BLOCK_K),
    swizzle=K_SWIZZLE
]()

Bank conflicts occur when multiple threads access different addresses in the same memory bank. Swizzling permutes the address pattern to spread accesses across banks.

2. Pipelined Loading

# Prefetch next V tile while computing QK
fn prefetch_v_tile():
    v_next_buffer.load_async(v_ptr_next)

mma[prefetch_function=prefetch_v_tile](
    qk_accumulator, q_buffer, k_buffer
)

While tensor cores compute Q@K, DMA engines load the next V tile. This overlaps compute and memory transfer.

3. Explicit Synchronization

# Post-QK barrier (required on AMD hardware)
barrier()

# Apply softmax
online_softmax(qk_buffer, m, d)

# Pre-PV barrier (empirically necessary for correctness)
barrier()

# PV accumulation
mma(output, p_buffer, v_buffer)

AMD GPUs have different memory ordering guarantees than NVIDIA—explicit barriers ensure correctness.

The Algorithm is Identical:

  • Online softmax with rescaling
  • Tiling to fit in fast memory
  • O(N) memory complexity

The Implementation Differs:

  • CPU: Exploit large caches, use BLAS libraries
  • GPU: Explicit memory hierarchy, maximize parallelism

This demonstrates the power of algorithm/hardware separation. Flash Attention’s mathematical insight (online softmax + tiling) applies to any memory hierarchy—CPU cache, GPU SRAM, even TPU HBM.

The core Flash Attention algorithm adapts to all these patterns—the tiling structure and online softmax remain unchanged, but each variant optimizes different aspects of the memory/compute trade-off.
